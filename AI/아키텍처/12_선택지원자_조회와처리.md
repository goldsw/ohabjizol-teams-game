# 선택 지원자 조회와 처리 분리
- 상태: 구현 완료·독립 소스 검토 이상 없음. 부모 Unity 컴파일·메뉴 Play 검증 완료함.
- 목표: 선택 팀 읽기와 점수·일정 처리를 분리하고 향후 특성 확장 경로 확보함.
- 기준: 2026-10-17 현재 소스. 오래된 graphify 자료 대신 아래 확정 소스를 기준으로 함.

## 1. 현재 책임과 보존 조건
- [InterviewSession](../../Assets/Scripts/Interview/Rules/InterviewSession.cs): BuildResult에서 ActualSum/FraudCount로 점수 계산, BuildScheduleResult에서 Team.Members 순회함.
- [TeamRoster](../../Assets/Scripts/Interview/Rules/TeamRoster.cs): 최대 4명·합류 순서·실제/표시 합계 유지, TryAdd는 internal임.
- [TeamMember](../../Assets/Scripts/Interview/Rules/TeamMember.cs): Applicant 원본과 1부터 시작하는 JoinOrder 보관함.
- [InterviewSummaryPresenter](../../Assets/Scripts/Interview/Runtime/InterviewSummaryPresenter.cs): 슬롯은 Team.Members, 현재 합계는 DisplayedSum 직접 읽음.
- [ResultGradeRule](../../Assets/Scripts/Interview/Rules/ResultGradeRule.cs): 핵심 직군·실제 스킬·사기 인원 기반 Evaluate API 유지함.
- [ParticipantScheduleResult](../../Assets/Scripts/Interview/Rules/ParticipantScheduleResult.cs): 생성자가 1~30일 일정 교집합 계산함.
- 기존 스탯 SO 13명·39직군, 별 UI, 표시/실제 스킬 차이, 결과·저장·재시도 동작 보존 필요함.
- Applicant 특성 스키마는 없음. 현재 문서에서 특성 필드·효과·플러그인 체계 신설하지 않음.

## 2. 확정 책임 경계
- 데이터 흐름: 기존 프로필 → 세션 Applicant → SelectedTeamQuery → 값 스냅샷 → 각 processor / 표시 projection임.
- TeamRoster: 선택 상태·정원·합류 순서 유지함. 스냅샷 저장소로 교체하지 않음.
- SelectedTeamQuery: 현재 선택 팀을 한 번 순회해 평가용 스냅샷 생성함. 점수·등급·충돌 계산하지 않음.
- InterviewScoreProcessor: 스냅샷으로 실제 합계·사기 수 산출 후 기존 점수 규칙 호출함.
- InterviewScheduleProcessor: 스냅샷과 프로젝트 일정으로 기존 일정 결과 생성함.
- SelectedTeamDisplayProjection: 스냅샷에서 공개 표시 항목만 새 객체로 생성하고 표시 합계 산출함.
- InterviewSession: 스냅샷 획득·처리 호출·기존 InterviewResult 조립 및 Result 보관 담당함.
- InterviewSummaryPresenter: 선택 팀 슬롯·표시 합계를 표시 DTO에서 읽고 화면 갱신만 담당함.

## 3. 값 스냅샷과 공개 표시 계약
- 내부 SelectedTeamSnapshot: 선택 순서의 IReadOnlyList<SelectedApplicantSnapshot>, Count 제공함.
- 내부 SelectedApplicantSnapshot: JoinOrder, CharacterId, Name, PrimaryRole, ActualSkills, DisplayedSkills, Kind, UnavailableSchedule 값 보관함.
- ExpectedSkills/FakeSkills는 현재 처리 입력에 불필요하므로 복제하지 않음. 표시 스킬은 기존 Applicant.DisplayedSkills 의미를 그대로 사용함.
- UI용 SelectedTeamDisplaySnapshot: Count, Members, DisplayedSum만 제공함.
- UI용 SelectedApplicantDisplay: JoinOrder, CharacterId, Name, PrimaryRole, DisplayedSkills만 제공함.
- UI DTO에 Applicant/TeamMember/평가 스냅샷 참조, ActualSkills, Kind, FraudCount, ExpectedSkills/FakeSkills 접근 경로 두지 않음.
- 모든 DTO는 생성 후 변경 불가함. 원본 컬렉션을 감싸기만 한 live view나 공개 Applicant[]로 대체하지 않음.
- 목록은 별도 저장소로 복사 후 읽기 전용 래핑함. 원본 배열·가변 리스트를 외부에서 회수할 수 없게 함.
- SkillSet·MonthlySchedule의 불변성이 확인되지 않으면 스킬 값·날짜 플래그를 방어 복사함. get-only 참조만으로 불변 취급하지 않음.
- 일정은 프로젝트/지원자 모두 포착 시점의 1~30일 값을 고정함. 기존 일정 타입을 쓸 때도 원본 변경 영향 차단 필요함.
- CharacterId는 기존 값을 보존함. 유일성을 가정하지 않고 선택 순서/JoinOrder로 슬롯 대응함.
- 빈 팀은 빈 Members·Count 0·SkillSet.Zero 표시 합계 반환함. null Applicant는 기존 추가 경로의 예외 계약 유지함.

## 4. 제안 API와 가시성
- Rules/SelectedTeamQuery.cs: internal static Capture(TeamRoster roster) → SelectedTeamSnapshot임.
- Rules/SelectedTeamSnapshot.cs: 내부 팀/지원자 값 DTO 배치함. UnityEngine·SO 의존성 추가하지 않음.
- Rules/SelectedTeamDisplaySnapshot.cs: 공개 표시 DTO와 내부 projection 배치함.
- InterviewSession.ReadSelectedTeam() → SelectedTeamDisplaySnapshot 공개함. 호출 시 최신 선택 상태의 새 표시 스냅샷 반환함.
- InterviewSession 내부 평가 경로만 SelectedTeamQuery.Capture(_team) 호출함. 평가 스냅샷을 public API로 내보내지 않음.
- Rules/InterviewScoreProcessor.cs: internal Process(SelectedTeamSnapshot, GameJamTheme) → InterviewScoreSummary임.
- InterviewScoreSummary: ActualSum, RequiredSkills, FraudCount, FulfillmentPercent, Grade, AccuracyPercent, IsClear 보관함.
- Rules/InterviewScheduleProcessor.cs: internal Process(SelectedTeamSnapshot, MonthlySchedule) → InterviewScheduleResult임.
- 위 파일명·API는 제안 계약임. 기존 API 실제 변경은 승인된 구현 단계에서 수행함.
- 새 인터페이스·DI 컨테이너·범용 파이프라인은 도입하지 않음. 현재 두 처리 책임만 구체 타입으로 분리함.

## 5. 처리 상세
- BuildResult 시작 시 평가 스냅샷을 한 번만 포착하고 점수/일정 processor 양쪽에 동일 객체 전달함.
- 점수는 합류 순서대로 ActualSkills를 SkillSet.Zero에 Add함. Kind == ApplicantKind.Fraud 인원만 집계함.
- 기존 FulfillmentRate.Percent, ResultGradeRule.Evaluate, StageAccuracyRule.Percent/IsClear 호출 순서·인자 의미 유지함.
- 검증 성공/실패 횟수는 선택 팀만으로 복원 불가함. 세션 누적값을 기존 InterviewResult 생성자에 그대로 전달함.
- Stage·RequiredSkills·AccuracyPercent·IsClear·Schedule을 포함한 기존 InterviewResult 형식 유지함.
- 일정 processor는 선택 순서대로 ParticipantScheduleResult(Name, UnavailableSchedule, ProjectSchedule) 생성함.
- 일정 교집합 계산은 기존 ParticipantScheduleResult 생성자에 위임함. 날짜 범위·인원 순서·중복 이름 동작 보존함.
- processor는 roster·세션·SO를 변경하지 않고 난수를 소비하지 않음. 재호출 시 같은 입력이면 같은 결과 반환함.
- 생성자 빈 지원자 종료, Accept/Reject 종료 시 BuildResult 호출 시점 유지함.
- 세션 CopyApplicants의 무작위 일정·가짜 품질 생성 유지함. query는 재추첨하지 않음.
- 표시 projection은 DisplayedSkills만 합산함. 실제 합계에서 표시 합계를 유도하지 않음.
- Presenter.Render는 ReadSelectedTeam을 한 번 호출해 슬롯과 현재 합계에 함께 사용함.
- 현재 면접자 별 UI의 Current.DisplayedSkills 바인딩·버튼/재시도/종료 문구는 기존 동작 유지함.

## 6. 호환 API와 이행 범위
- InterviewSession 생성자·Team·Applicants·Current·Accept/Reject·Result의 기존 계약 유지함.
- TeamRoster.Members/Count/DisplayedSum/ActualSum/FraudCount 및 TryAdd 계약 유지함.
- ResultGradeRule.Evaluate·ParticipantScheduleResult 생성자·InterviewResult 외부 형식 유지함.
- 기존 roster 합계는 호환용으로 남기되 새 결과 경로는 snapshot processor를 권위로 삼음. 계산식 중복에 따른 불일치 위험 관리 필요함.
- 신규 표시 DTO는 데이터 노출 경계임. 기존 Team/Applicants/Result 공개 API까지 접근 차단하는 보안 격리는 아님.
- 신규 Presenter 선택 팀 경로에서 원본 접근 제거함. 기존 공개 API 축소·전체 UI 교체·asmdef 재편은 별도 범위임.
- 스탯 SO/에셋/별 프리팹/기존 직군 값 수정 없이 규칙 클래스 추가와 Session/Presenter 연결 변경으로 한정함.
- 설계 시점 기록: 문서만 작성함. 코드·CLI·테스트·커밋·그래프 재구축·네트워크 작업 수행하지 않음.

## 7. 향후 지원자 특성 확장
- 스키마 확정 후 기존 프로필에 타입이 정해진 특성 데이터 추가 → 세션 Applicant 런타임 복사 → 평가 snapshot 값 복사 → 해당 processor 규칙 적용 순서임.
- CopyApplicants에서 새 데이터가 누락되지 않게 원본→런타임 복사를 함께 수정해야 함.
- 공개 가능한 특성만 표시 projection에 별도로 허용함. 숨김 효과/실제값을 UI DTO에 자동 복사하지 않음.
- 특성의 점수/일정 영향이 확정된 범위만 해당 processor에 추가함. dictionary<object>·가상 trait·플러그인 registry 신설 보류함.

## 8. 구현 인계 위험과 수용 기준
- 위험: readonly 컬렉션 내부 원본 참조, 가변 SkillSet/일정 공유, public DTO를 통한 숨김값 누출 가능함.
- 위험: roster 합계와 processor 계산 불일치, 합류 순서 변화, 재포착 간 값 차이, 특성 런타임 복사 누락 가능함.
- 인계 전 확인: 값 타입 불변성·기존 복사 API·외부 호출부를 Luna High 검색으로 확정하고 구현 범위를 고정해야 함.
- 수용 기준: 정상/사기/빈 팀·4명·일정 충돌의 기존 점수/등급/결과 동일함.
- 수용 기준: 표시 합계가 실제 합계와 다른 경우도 기존 UI 유지, DTO만으로 실제 스탯 접근 불가함.
- 수용 기준: 포착 후 원본/선택 변경이 이전 스냅샷에 영향 없고 두 processor는 같은 포착값 사용함.
- 수용 기준은 설계 시점 검토 항목임. 독립 검토는 소스만 확인함. 실행 검증은 부모 완료 보고 기준임.
