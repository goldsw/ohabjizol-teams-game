# 면접 흐름 책임
## 소유자
- StageContext: 확정한 RunId·StageDefinition과 문서키 생성 정보 담당함.
- StageManager: InterviewSession 생성·판정·지원자 전환·완료 조율 담당함. 도메인 규칙은 기존 InterviewSession에 유지함.
- QuestionController: 지원자별 질문 상태·진행·취소 담당함. 상태를 UI 밖에 둠.
- 기능 presenter: 질문 연출·지원자 표시·요약·알림 담당함. 기존 통화/질문/다운로드 view와 DocumentWorkspace를 재사용함.
- InterviewScreen: Inspector 입력 참조와 요청 이벤트·호환 조회 API 담당함. 세부 연출·문서 정리·지원자 전환은 기능 클래스에 둠.

## 이벤트와 수명
- Screen 입력 요청 → 담당 처리 → 상태 소유자 이벤트 → presenter/view 갱신 구조임.
- StageManager는 지원자 변경 직전에 이전 응답·문서·알림 정리를 요청하고, 새 지원자 상태를 확정한 후 변경 이벤트를 발행함.
- 단순 숨김은 표시 동작임. Screen 비활성화는 응답을 취소하며, 재활성화 시 같은 지원자 상태를 다시 표시함.
- 질문은 미사용/응답 중/완료 상태로 구분함. 취소된 진행 중 질문은 미사용으로 복구함.
- UsedQuestionCount는 기존 공개 API의 예약 포함 의미를 유지할 수 있음. 완료 전 소진으로 남지 않도록 취소 복구 필수임.
- 응답이 이전 지원자에서 새 지원자로 유출되지 않도록 요청 식별값과 현재 지원자를 확인함.
- 합격/불합격은 질문 진행 중에도 가능함. 재진입 판정과 중복 완료를 차단함.
- 완료 콜백의 저장 성공 후에만 Result/HandoffSceneName으로 씬 전환 가능한 결과를 노출함. 저장 실패는 완료 대기 상태로 유지하며 재시도 경로를 제공함.

## 호환과 구현 경계
- InterviewScreen의 직렬화 필드·initialDocuments·discordVisible·public API 유지함.
- Bake 생성은 EditMode 전용임. 필요하면 partial Authoring 파일로 분리하되 원본 스크립트 GUID를 유지함.
- RuntimeProbe의 _response 참조와 질문 사용 수 검증도 새 상태 계약과 일치시킴.
- A가 면접 클래스와 probe를 수정함. 저장 서비스의 내부 구현은 B 소유임.
