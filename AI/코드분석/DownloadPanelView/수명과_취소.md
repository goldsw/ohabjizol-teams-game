# 수명과 취소

## 닫기·비활성화 조건

- Close: 위치 이동만 수행함. 활성 상태·진행 작업 유지, Runtime Tick 지속 → 패널을 닫아도 다운로드 계속됨(View 97, 104–110행, Runtime 136–143행).
- CloseImmediate: 슬라이드만 중단하고 닫힌 위치 적용함. 취소 없음(View 98–103행).
- 패널 단독 OnDisable: 새 시작은 차단되나 기존 작업은 유지됨. Screen/Runtime이 활성 상태면 TickDownloads에 활성 가드가 없어 진행·완료 가능함(View 34, 62, 93행, Presenter 38행).
- Screen까지 비활성화하는 루트/화면 비활성화: Runtime.Disable 경유 Tick 중단·미완료 작업 취소함. 전체 화면 밖에서도 유지하는 기능 계약은 아님(Screen 130–134행, Runtime 105–112행).
- 슬라이드와 다운로드 Tick 모두 unscaledDeltaTime 사용함. 화면 활성 중 두 경로 모두 게임 시간 배율에 의존하지 않음(View 117행, Runtime 141행).
- 완료된 종류는 CancelPending 후에도 진행률 1 유지함. 미완료는 0으로 초기화함. 키가 바뀌면 완료 여부·진행률 모두 초기화함(Controller 26–46행).

## 지원자 교체·취소·유효성

- Stage.Decide: ApplicantChanging→세션 Accept/Reject→ApplicantChanged 순서임(Stage 44–55행).
- Changing→Runtime.ClearApplicant→Applicant.Clear→Presenter.Clear→BindContext(null) 실행함. workspace도 ClearApplicant 호출함(Runtime 79, 186–191행, Applicant 25–35행, Presenter 42–48행).
- Changed→Runtime.BindApplicant→Applicant.Render→Presenter.Bind→BindContext(newKey), workspace.BindApplicant 실행함(Runtime 80, 193–197행, Applicant 52–68행, Presenter 30–36행).
- BindContext는 키가 같으면 유지, 달라지면 CancelPending으로 generation 증가·Request 제거 후 완료/진행률 초기화함(Controller 26–46행).
- IsCurrent는 요청의 generation·지원자 키를 비교함. Presenter도 자기 현재 키와 대조하므로 이전 지원자 요청이 새 workspace로 반영되는 것을 방어함(Controller 22–24행, Presenter 54–56행).
- 명시적 CancelPending·Presenter.Unsubscribe·View.OnDestroy도 취소 경로임. Close는 취소 경로가 아님(View 33, 86, 97행, Presenter 25행).
